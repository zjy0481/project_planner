# Project Planner 语言设置与文案表修改方案

日期：2026-10-09

状态：用户已于 2026-10-09 授权实施，修改及验证已完成

保留 `$project-planner` 的全局语言偏好，以当前对话语言作为未设置偏好时的默认选择。固定标题、图例、状态、说明和详情弹窗统一通过文案表获取。遇到尚未具备文案的目标语言时，由 LLM 翻译完整文案表，完成自动校验和独立的全量语义对照后保存，供后续项目复用。

本方案是一份独立的实施依据，覆盖语言选择、偏好保存、文案结构、新语言扩充、审查、兼容性和验收。它不要求读者先阅读旧方案。实施完成后保留本文作为修改范围与验收依据。

## 1 目标与现有实现

当前 LLM 编写计划摘要、需求映射、任务描述、假设和风险。Python 脚本根据计划输入计算排程，并生成 `schedule.json`、`plan.md`、`gantt.svg` 和 `gantt.html`。脚本还负责输出固定文案，因此仅指定 LLM 的回复语言不能改变全部产物文字。

现有 `scripts/locales/en.json` 和 `scripts/locales/zh-CN.json` 各有 59 个固定文案键。它们已经是按语言划分的文案表，但生成器和配置助手把语言限制为中英两种，尚无新语言的翻译、审查和长期复用流程。技能目前还会在全局语言为空时先询问偏好；本方案将该询问移到最终交付之后。

修改保持现有确定性排程、相对工作量、依赖交付门槛、资源锁、未知外部事件阻塞、文件保护和四种主要产物。技能指令继续使用英文；用户交流、生成产物和指令文本的语言分别确定。

## 2 三类语言数据

| 数据 | 保存位置 | 用途 | 何时变化 |
| --- | --- | --- | --- |
| 技能默认语言 | 安装副本的 `config.json` 中的 `language` | 使用该副本的项目共用的用户偏好 | 用户明确要求保存、更改或清空时 |
| 本次输出语言 | 当前计划的 `plan-input.json`、`schedule.json` 和审查记录 | 确定正文、固定文案和审查报告的实际语言 | 本次明确要求或解析规则决定；切换后重新生成和审查 |
| 可复用文案表 | 技能自带目录或技能专属持久目录 | 按固定键提供目标语言文字 | 增加语言、修订译文或源文案变化时 |

这里的“全局”仅指使用同一技能安装副本的项目，不是 Codex 全局配置。语言文案保存和用户偏好保存是两种操作：增加日语文案不会把默认语言改成日语；使用一次英文也不会自动保存英文偏好。

保留初始配置和其他已存在设置：

```json
{
  "language": null,
  "max_parallel": null,
  "max_review_revisions": 2
}
```

`language: null` 表示跟随本次语言解析规则，不在生成开始时触发偏好询问。`max_parallel` 仍表示计划中普通任务的容量，`max_review_revisions` 仍只限制计划初审后的修订复审。本方案不增加其他全局配置项。

## 3 输出语言选择

遵守适用的上级指令，主代理按以下顺序确定本次产物语言：

1. 本次明确指定的产物语言。
2. 更新已有计划时，该计划已记录的语言；用户明确要求切换时采用新要求。
3. 技能配置中非空的默认语言。
4. 当前对话中用户实质性请求的主要语言。
5. 请求只有技能调用标记、没有可参考的语言偏好或实质性对话时，使用 `en`。

英文技能文档、代码、引用、文件内容和零散外语词不改变对话语言判断。混合语言确实使目标不明确时，询问本次产物语言；这是完成当前任务所需的澄清，与是否保存默认语言分开。

主代理将实际采用的语言代码显式写入计划输入，并记录选择依据。生成器只读取本次输入和确定的文案数据，不读取可变的全局偏好。原始需求逐字保留，代码、路径、任务 ID、需求 ID、资源锁名称、JSON 键和协议值保持原样。

语言名称由主代理转换为规范代码，例如简体中文为 `zh-CN`、英文为 `en`、日语为 `ja`。配置助手接受合法语言代码或 `null`；生成器另外检查该语言是否已具备完整、有效的文案。语言代码不再硬编码为中英枚举，也不能直接作为未经验证的文件路径。

| 用户请求或配置状态 | 当前计划的实际语言 | 技能全局配置 | 交付末尾行为 |
| --- | --- | --- | --- |
| 配置为空，用中文要求新建计划 | 简体中文 | 保持 `null` | 提示可将简体中文设为默认 |
| 配置为空，用中文明确要求英文产物 | 英文 | 保持 `null` | 提示可将英文设为默认 |
| 配置已保存英文，用中文要求新建计划 | 英文 | 保持 `en` | 不追加首次设置提示 |
| 配置已保存中文，本次明确要求日语 | 日语；缺少文案时先完成扩充与核验 | 保持 `zh-CN` | 不自动改变默认值 |
| 更新已有英文计划，未要求改语言 | 英文 | 保持原值 | 若配置仍为空，提示可保存英文默认 |
| 用户明确要求默认语言设为日语 | 不触发已交付计划的重新生成 | 更新为 `ja` | 告知设置结果及适用范围 |
| 用户明确要求清空默认语言 | 已交付产物保持原样 | 更新为 `null` | 后续新计划按对话语言解析 |

全局偏好为空和计划输入语言为空具有不同含义：全局 `null` 有效；计划输入显式 `null` 仍无效，因为实际生成必须使用确定的语言。

## 4 交付后保存语言偏好

配置为空时，先完成计划建模、文案准备、生成和正常独立审查。成功交付经过审查的产物后，在最终回复末尾追加一次可选提示，不暂停当前任务等待回答。若未能完成交付，优先说明未完成事项，本轮不追加偏好设置提示。

以本次实际产物语言填充提示，而不是直接使用对话语言。简体中文示例：

> 是否要将本次使用的简体中文设为 `$project-planner` 生成项目计划与甘特图的默认语言？如需设置，请回复：
>
> **将 `$project-planner` 的默认语言设为简体中文。**
>
> 该设置将用于后续项目；不设置则继续跟随对话语言。

已有默认语言时不追加该提示。配置缺失时按虚拟默认值处理，交付前的读取不会创建配置文件。用户不回复、仅指定本次语言或翻译扩充成功，都不会授权保存默认值。

收到明确的设置指令后，主代理只更新获授权的配置项，保留其他配置和自定义字段，使用现有原子保存机制。保存失败时准确报告失败，不声称默认值已更新。用户可以在任意时点主动更改或清空偏好，不必等待末尾提示。

保存偏好只影响后续计划，不改变已交付文件或使其已有审查失效。如果用户同时要求翻译当前计划，另行按本次语言变更处理，重生成并完整复审。

用户可以先保存一种尚未具备文案的合法语言偏好。该操作只保存偏好；下一次生成时仍须完成对应文案的扩充和核验，保存配置不代表该语言已经具备经过检查的完整产物能力。

## 5 文案表结构

采用每种语言一份 UTF-8 JSON，继续复用现有中英文目录。CSV 可以存储这些内容，但现有文案包含长句、换行和占位符，JSON 更贴近当前生成器，也便于按键校验。首版无需引入数据库、在线翻译服务或新的模板框架。

文案键表示用途，文字值可以是词语、完整句子或模板。生成器通过“语言代码与固定键”查表，例如 `zh-CN + plan_title`。不用中文词语作为键，也不把不同位置的“标题”合并成一个用途不明的词条。

| 固定键 | 中文示例 | 英文示例 |
| --- | --- | --- |
| `plan_title` | 项目计划 | Project plan |
| `chart_title` | 项目甘特图 | Project Gantt chart |
| `close` | 关闭 | Close |
| `blocked_count` | `{count}` 个任务因外部条件待确认而阻塞 | `{count}` tasks blocked by unknown external readiness |

任务名称、摘要、描述、假设、风险和验收条件继续由 LLM 按本次语言编写，不收录为全局固定文案。固定文案中的占位符由程序填入数据，翻译可调整占位符的位置，但保留变量名称和用途。整句翻译应保留语序与语法，避免逐词拼接。

英文文案作为源文案，中文作为既有语义对照。新增语言翻译时，同时提供两份完整文案和使用场景。若中英文存在含义冲突，先明确并修正源文案，不能自行任选一份或折中翻译。

## 6 文案保存与复用

技术落地建议保留 `scripts/locales/` 中的官方中英文案，并新增 `<skill-dir>/user-locales/` 保存经核验的新语言。该目录由使用此技能安装副本的项目共用，技能升级时与 `config.json` 一起保留；普通生成不覆盖内置源文案。

建议每个新增语言使用一个 JSON 文件，同时包含文案、源文案哈希和语义核验记录。把正式文案和它的核验依据保存在同一文件中，可以用一次原子替换发布，避免仅写入译文、未写入核验记录的中间状态。

建议文件使用 `language`、`version`、`messages`、`source_hashes`、`messages_sha256` 和 `semantic_review` 字段，分别表示以下信息；实施时在本地化说明中定义完整结构：

- 语言代码、格式版本和完整的 `messages` 对象。
- 英文源文案、中文对照文案及翻译上下文的 SHA-256。
- 被核验目标文案内容的 SHA-256、核验结论和全量覆盖结果。
- 每条文案的对照结论，以及问题、修正和最终核验依据。

只有内容哈希一致、源文案仍一致且全量语义核验通过的文案可用于正式复用。文件存在、字段中写着“通过”或结构校验成功，均不能单独替代完整核验记录。

新翻译和修订先保存在候选文件中。核验通过后发布正式文案；失败的候选保留问题记录，不替换原有有效版本。手动修改正式译文会使内容哈希失配，须重新核验后才能使用。

源文案发生变化时，对应语言的既有核验失效。可以只重新翻译新增或受影响条目，但发布前必须对更新后的整份文案与中英文源文案进行全量语义对照。源文案和目标内容都未变化时，直接复用，不重复翻译或语义审查。

技能更新保留用户文案文件，但不因“保留文件”而沿用失效的核验结果。生成时检查源文案哈希，决定是否需要重新准备目标语言。新语言文案保存和源文案升级由同一个文案加载模块协调，生成器继续使用统一查表接口。

## 7 新语言翻译与全量语义核验

进入新语言分支前，读取完整的英文源文案、中文对照和本地化说明，冻结其哈希。当前已有 59 项，验收以实际完整键集合为准，不把 59 写成永久固定数量。

1. **翻译完整文案。** 当前主代理的 LLM 根据目标语言、全部条目及用途生成候选文案。翻译保持计划术语与相对工作量含义，不生成排程数值，不修改源文案或协议键。
2. **进行自动校验。** 检查语言代码、JSON 格式、完整键集合、非空字符串、占位符和格式化规则；用代表性参数验证模板能正确填充，检查显示文字经过现有 Markdown、HTML、SVG 和脚本数据转义。
3. **独立全量语义对照。** 使用不继承父对话上下文的独立审查者，提供完整中英文案、目标文案、用途说明和稳定文件哈希。逐键对照所有条目，包括此次计划不会显示的条目。
4. **裁决并修正。** 主代理回到三份实际文案核验审查意见。对有效问题修改候选，重新执行自动校验，并用新的独立审查者重新全量核验。记录采纳、部分采纳和驳回的依据。
5. **发布并使用。** 全量覆盖、结构校验、语义结论和审查前、所读、审查后哈希均一致后，原子保存正式文案，再生成计划产物。

语义核验至少逐条检查：

- 是否完整保留含义、条件、否定、限制和不确定性，是否遗漏或添加承诺。
- 同类术语是否一致，任务、里程碑、外部事件、依赖和资源锁是否准确区分。
- “粗略工作量”“相对位置”“实际工期”是否准确区分；未知就绪条件是否仍表示阻塞。
- `scheduled` 和 `blocked` 等状态的显示译文是否正确，不改变底层协议值。
- 数量、单位及占位符用途是否一致；变量位置是否符合目标语言表达。
- 按钮、标题、图例和说明在各自使用场景中是否自然且不引起误解。

核验结果使用 `PASS`、`REVISE`、`INCOMPLETE`，并列出每个键的结论和具体证据。`PASS` 要求全部条目完成对照，无未解决的语义错误；审查未完成、存在源文案冲突或哈希失配时不能发布。

翻译和核验不依赖额外的在线翻译 API。内部审查者的模型、容量和委派遵守实际项目或运行环境的规则。本方案不改变计划独立审查固定使用 `gpt-6.1-sol`、`high`、`fork_turns="none"` 的要求。

文案修订与计划修订是不同阶段，不消耗或重新解释 `max_review_revisions`。技术落地建议为一次文案准备限定初审加最多两次修订复审，达到边界仍未通过则保留候选、报告问题并停止目标语言正式生成；该边界写入本地化流程说明，本轮不新增配置字段。

## 8 生成与审查中的固定文案快照

每份计划保存本次使用的完整文案快照，例如 `<output-dir>/locale-snapshot.json`，包含实际文案、语言、源文案哈希和核验依据。生成器从明确的快照读取固定文字，避免审查期间共享文案更新影响当前产物。

`plan-input.json` 保留 `language`，并建议增加 `localization` 对象，以 `snapshot` 指定 `locale-snapshot.json`，以 `messages_sha256` 记录实际文案内容哈希；`schedule.json` 回显语言和该对象。快照路径按计划目录解析，生成器显式接收输入，不按用户语言拼接任意路径。旧中英输入的兼容规则见第 10 节。

四种主要产物继续从同一份输入、排程和文案快照生成。额外的快照是复现与审查依据，不改变四种主要产物的名称，也不改变排程语义。快照保存同样使用生成标识、原子写入和覆盖保护，同名非本技能文件应保留。

计划独立审查增加文案快照作为必读证据。原始需求、计划输入、排程、Markdown、SVG、HTML 的原有六文件哈希校验继续执行，同时把快照纳入相同的三方哈希一致性检查。图表和实际 HTML 详情弹窗的视觉检查继续执行，检查目标语言、文字截断、换行、字体显示和关键说明。

文案表语义核验检查所有固定条目；计划审查检查实际正文、排程、显示结果和完整交付，两者分别完成。中英内置文案在本次实施时也应完成一次全量对照，作为后续新语言核验的可靠基线。

## 9 失败与保存边界

| 情况 | 处理 |
| --- | --- |
| 翻译遗漏键或破坏占位符 | 修正候选并重跑校验；正式文案保持原样 |
| 语义核验发现问题或未完成 | 保留证据，修正并完整复审；未通过时不进入正式生成 |
| 中英文源文案冲突 | 明确冲突并修正基线，再翻译和全量核验 |
| 已有文案被修改或源文案升级 | 核验失效，重新准备对应语言 |
| 无法长期保存已核验文案 | 告知复用保存失败；若计划目录可写，保存已核验的本次快照并继续生成，不声称已完成长期扩充 |
| 目标语言仍无法准备完成 | 报告具体问题；需要改用另一种语言时取得用户明确选择，不静默输出英文 |
| 用户语言偏好保存失败 | 报告配置未更新，已经交付的计划保持有效 |

请求以一种语言生成计划，包含准备必要文案的步骤；翻译通过后的长期保存属于文案复用流程，不授权修改用户默认语言。实际文件写入仍遵守环境权限和明确的保存目录。技能读取缺失配置继续使用虚拟默认值，读取无效配置继续报告错误，不能冒充已有用户偏好。

## 10 修改范围与兼容性

| 文件或范围 | 拟修改内容 |

| `project-planner/SKILL.md` | 集中定义语言解析和交付后提示；新增语言分支指向本地化说明，保留规划和独立审查闭环 |
| `project-planner/references/localization.md`，新增 | 记录文案用途、翻译步骤、全量语义核验、修订边界、持久保存和失效规则 |

| `project-planner/references/review.md` | 增加固定文案快照及目标语言检查，保持原有全文审查、视觉检查、裁决和三方哈希闭环 |
| `project-planner/scripts/skill_config.py` | 接受规范语言代码及 `null`，保留显式授权保存、原子写入和未知字段保护 |
| 文案加载与校验模块，新增或从生成器提取 | 统一加载内置和新增语言，验证文案、核验记录及源哈希，输出固定快照 |
| `project-planner/scripts/build_plan.py` | 从选定文案数据查表渲染，正确转义新译文，保留确定性排程与文件保护 |
| `project-planner/scripts/locales/` | 保留中英完整文案，核对基线语义并按需修正文案 |
| `project-planner/user-locales/`，新增运行时目录 | 保存经全量核验的新语言；更新技能时保留，不默认发布用户运行时文件 |
| 中英文 README、相关测试、示例、`docs/requirements.md` | 实施时同步实际行为、安装升级要求、快照和新语言验收；此次方案编写不更新这些文件 |

保留当前中英语言代码、文案键、配置默认值和旧配置中的用户偏好。直接运行生成器时，旧输入缺少 `language` 仍默认英文；技能调用会根据当前规则显式补充实际语言。计划输入显式 `null` 仍应拒绝。

旧的中英输入没有文案快照时，可以使用对应内置文案作为兼容入口；新的技能生成流程始终保存快照。新增语言的生成要求明确的有效文案证据，不能仅凭一个语言代码承诺完整交付。

示例和旧审查报告作为其当时版本的证据保留；输入契约和文案变化后重新生成的计划须获得新的审查。技能安装或升级必须保留已有 `config.json`、自定义字段和 `user-locales/`，避免将运行时翻译文件意外提交到公共仓库。

## 11 实施顺序

1. 核验中英文案基线，统一固定键、占位符和用途说明，完成全量语义对照。
2. 实现共享的语言代码与文案加载、校验、发布、快照规则，接入生成器及配置助手。
3. 更新技能语言选择、按需翻译、全量核验和交付末尾提示流程。
4. 把文案快照接入计划独立审查，同时保持原有审查闭环。
5. 同步契约、需求、README、升级保护和必要测试，完成中英回归及一种新增语言的完整验证。

实施仅涉及本技能和配套文档；不创建 GitHub Issue、PR，不更改项目政策，也不实现其他项目业务代码。

## 12 验收要求

| 场景 | 必须观察到的结果 |
| --- | --- |
| 默认为空，中文对话 | 不在开始时询问偏好；完整交付中文产物后末尾提示保存中文默认；配置仍为空 |
| 默认为空，明确要求英文 | 四种主要产物及计划审查报告使用英文，末尾提示保存英文；不会误存对话使用的中文 |
| 已有英文默认，本次中文对话 | 新计划使用英文，不追加首次设置提示 |
| 已有中文默认，本次指定日语 | 日语优先，仅影响当前计划；全局中文偏好保持原样 |
| 明确保存或清空默认语言 | 只修改获授权字段，其他及自定义字段保留；不重新生成已交付计划 |
| 日语文案不存在 | LLM 生成完整候选，自动校验和独立全量语义核验通过后保存，再开始正式生成 |
| 目标语言文案存在且未变化 | 直接复用，不重复翻译或全量语义核验 |
| 仅本次未使用的词条存在错误 | 全量核验仍发现错误，错误候选不能发布 |
| 源文案变化或目标文案被手改 | 已有核验失效；修正后重新全量核验 |
| 中英文源文案含义冲突 | 报告并处理源文案冲突，不通过任选一份来发布翻译 |
| 同一计划更换中、英、日显示语言 | 在任务、依赖、资源锁和数值输入一致时，排程起止、阻塞关系和并行约束一致 |
| 长句、占位符、特殊字符和详情弹窗 | 文案正确填充、转义和显示；没有遗漏、语义漂移或错误截断 |
| 共享文案在计划生成后变化 | 已保存的本次快照仍可复现；审查针对实际快照和产物 |
| 空计划、未知外部条件、零修订上限 | 原有空状态、阻塞说明和完整初审要求继续成立 |
| 更新技能 | 用户偏好和新增语言文件保留；过期文案通过哈希检测，不假定仍有效 |
| 新语言核验未完成或保存失败 | 准确披露具体状态，不静默改语言，不声称已发布、已长期保存或已完成审查 |

代码测试验证结构、保存、失效、排程不变性和转义；独立语义核验验证完整译文；实际浏览器或可追溯截图验证图表和 HTML 详情。三种检查分别提供证据，不能仅凭字符串存在或 JSON 合法宣称语言支持已通过验收。
