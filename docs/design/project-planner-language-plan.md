# Project Planner 语言适配修改方案

日期：2026-10-09  
状态：用户已于 2026-10-09 授权实施，更新与验收已完成

为技能新增独立的 `config.json`，保存跨项目共用的语言和规划默认值，再为规划文档、甘特图和审查报告增加明确的输出语言契约，首版支持简体中文与英文；随后将技能指令及其参考文档迁移为英文权威版本。指令语言、与用户交流的语言和生成产物的语言分别确定，英文指令不应使中文用户默认收到英文产物。

## 目标和范围

语言选择应贯穿需求建模、确定性生成、独立审查和最终交付。用户明确指定英文产物时，即使需求和对话是中文，文档正文、图例、状态和交互界面也应使用英文。

本次修改涉及技能配置中的全局偏好、语言规则、输入契约、显示文案、图表布局、审查协议和使用说明。现有排程算法、相对工作量语义、文件名、生成文件保护、审查哈希机制以及 `gpt-6.1-sol` / `high` 审查设置继续适用。

首版提供 `zh-CN` 和 `en` 两种语言。其他语言需要后续补充完整文案与视觉验证，不承诺任意语言已经可用。

## 当前实现的问题

| 位置 | 当前行为 | 需要修改的原因 |
| --- | --- | --- |
| [SKILL.md](../../project-planner/SKILL.md) | 描述和正文要求中文规划文档，默认单位也直接写成中文 | 输出语言不能随用户偏好确定 |
| [输入契约](../../project-planner/references/schema.md) | 没有语言字段 | 生成器和独立审查者缺少同一份明确依据 |
| [生成脚本](../../project-planner/scripts/build_plan.py) | Markdown、SVG 和 HTML 的固定文案写死为中文，HTML 固定 `lang="zh-CN"` | 翻译任务正文仍会得到混合语言产物 |
| [审查协议](../../project-planner/references/review.md) | 审查对象称为中文规划，没有输出语言检查 | 无父对话上下文的审查者无法恢复用户偏好 |
| [界面元数据](../../project-planner/agents/openai.yaml) | 简介承诺中文规划文档 | 需要与新能力保持一致 |
| 中英文 README | 使用说明宣称产物固定中文 | 会误导使用者 |

生成脚本目前会显式重建规范化输入及排程对象。因此，仅在输入 JSON 中添加 `language` 不会自动传递到输出，必须同时修改 `validate_plan` 和 `build_schedule`。

## 语言选择规则

技能配置项统一采用小写命名。`config.json` 中的 `language` 初始值为 `null`，表示用户尚未保存语言偏好。英文 `en` 是技能的运行默认值；使用默认英文不会自动把配置中的 `language` 改为 `en`。

主代理在建模前读取 `<skill-dir>/config.json`，再按以下顺序确定本次输出语言：

1. 本次任务明确指定的产物语言，包括本次明确适用的用户偏好。
2. 更新已有计划时，其输入中已记录的输出语言；用户要求切换时采用新要求。
3. 技能配置中非空且受支持的 `language`。
4. 技能默认语言 `en`。

适用的上级指令及用户明确要求仍优先。对话、需求原文和技能指令使用的语言不自动写入全局配置，也不替代这个明确的偏好选择过程。

检测到技能配置中 `language: null` 时，主代理询问用户偏好的输出语言，并同时询问是否保存为本技能的全局偏好。如果本次请求已明确语言，只需询问是否保存该语言。用户授权保存后，更新 `config.json` 的 `language`，后续调用直接使用已保存的语言。每次技能调用内询问一次，避免同一次生成或复审重复提问。用户尚未回答时，可以按前述优先级继续准备计划；没有其他明确选择时使用英文，并说明采用的是默认语言。

用户选择其他语言后，更新本次输入并重新生成需要变化的产物；最终独立审查必须对应实际交付语言及文件。用户未回复时可以继续交付经过完整审查的英文默认产物，但不得声称英文是用户已确认的偏好。如果用户明确表示需要等待其选择，则等待后再完成依赖该选择的交付。

新的 skill 调用始终将实际采用的语言写入 `plan-input.json`。生成器只读取本次输入，不读取或修改全局偏好。直接运行脚本的旧输入缺少语言字段时，改为默认英文；这是相对当前中文默认值的有意行为变更，应在更新说明中注明。要保留已有中文示例的显示语言，为其输入显式补充 `language: "zh-CN"`。

建议在 SKILL.md 的输入阶段集中加入以下规则，其他阶段通过语言字段执行和验收：

> Read the skill-wide language preference from <skill-dir>/config.json before modeling. Its initial value is null. When it is null, ask for the user's preferred output language and whether to save it in this skill's configuration. Update the configuration only when the user explicitly agrees; later calls use the saved preference. Resolve the output language from the current task's explicit request, the recorded language of an existing plan, the saved skill preference, and finally the English default, in that order, subject to higher-priority instructions. Continue with the resolved language while an optional answer is pending. Record the effective language in <output-dir>/plan-input.json so the generator and reviewer can reproduce the result. Write authored planning content, chart labels, and review reports in that language. Preserve source requirements verbatim and keep identifiers, paths, JSON keys, and protocol values unchanged. Using the default does not establish or save a user preference. The language of these instructions does not determine the output language.

在同一位置说明首版支持范围，并规定：对于不受支持的目标语言，主代理说明限制，请用户选择受支持语言或另行扩展支持；不得静默替换，也不得先承诺目标语言的完整产物。

## 技能全局配置

全局配置指本技能自身跨项目共用的配置，保存在 `<skill-dir>/config.json`。它不属于 Codex 的全局配置。`plan-input.json` 保持现有用途，只记录一份计划的需求、任务、排程约束及实际采用的设置。

| 位置 | 字段 | 作用 |
| --- | --- | --- |
| `<skill-dir>/config.json` | `language`、`max_parallel` 等 | 本技能跨项目共用的偏好与默认值 |
| `<output-dir>/plan-input.json` | `language`、`max_parallel` 及需求和任务字段 | 当前计划的完整输入，记录本次实际采用的设置，使生成和审查可以复现 |

技能源目录新增 `project-planner/config.json`，安装时随完整技能目录分发；主代理以实际技能目录定位该配置，不依赖当前工作目录。建议首版初始内容为：

```json
{
  "language": null,
  "max_parallel": null,
  "max_review_revisions": 2
}
```

其中 `language` 的初始值与授权更新流程按用户要求设计，`max_parallel` 作为规划容量默认值；`max_review_revisions` 是建议补充的配置项，默认沿用当前最多两轮修订后复审的规则。其他候选项不自动加入首版。

### 配置项建议

| 配置项 | 初始值或建议默认值 | 作用与边界 | 建议范围 |
| --- | --- | --- | --- |
| `language` | `null` | 保存输出语言偏好；首版可选 `zh-CN`、`en`，未设置时询问并允许按默认英文继续 | 首版 |
| `max_parallel` | `null` | 规划中普通任务可同时开展的数量；正整数表示有容量上限，`null` 表示容量未知的理论排程 | 首版 |
| `max_review_revisions` | `2` | 初次审查后最多允许的修订后复审轮次；非负整数，`0` 表示只进行初次审查；达到上限仍有问题则交付待决草稿 | 建议首版补充 |
| `review_model` | `gpt-6.1-sol` | 调整独立审查模型；需要核验环境能力，不能静默替换或跳过审查 | 可后续补充，首版保持现有设置 |
| `review_reasoning_effort` | `high` | 调整审查推理强度，需要与模型支持的参数组合核验 | 可后续补充，首版保持现有设置 |

`max_parallel` 表示规划中的任务容量，不是 Codex 同时运行的代理数或审查者数量。跨项目通常只能作为默认值，不能覆盖本次项目已明确的团队容量。新的计划优先采用本次明确要求，其次采用适用的项目约束，再采用技能默认配置；更新已有计划时，保留其容量，除非用户明确要求修改。`null` 继续按现有规范披露为容量未知，不必像语言偏好一样自动触发询问。

语言以外的配置项同样只有在用户明确要求修改本技能默认值时才持久化。用户仅为当前项目指定最大并行数，不应自动改变 `config.json`。

不建议首版保存需求路径、任务列表、输出目录、资源锁或具体技术选型，这些内容依赖当前项目。工作量单位按语言提供默认显示文案；避免再用一个固定全局单位造成语言混杂。强制独立审查、视觉检查和哈希一致性是完成要求，不作为可关闭的普通偏好开关。

### 语言选择后的行为

下表只说明本次产物使用什么语言，以及是否更新技能配置；不使用“当前计划写入 language”表述。技术上的实际参数记录在后文输入契约中定义。

| 用户回应或配置状态 | 本次产物语言 | 技能配置是否更新 |
| --- | --- | --- |
| 配置中的 `language` 为 `null`，用户未回复 | 无其他明确语言要求时使用默认英文 | 不更新，`language` 仍为 `null` |
| 用户选择中文，仅用于本次 | 中文 | 不更新，保留现有配置 |
| 用户选择中文，并授权保存为技能默认语言 | 中文 | 将 `config.json` 中的 `language` 更新为 `"zh-CN"` |
| 用户选择英文，并授权保存为技能默认语言 | 英文 | 将 `config.json` 中的 `language` 更新为 `"en"` |
| 配置已保存中文，本次没有其他明确语言要求 | 中文 | 不更新，也不重复询问语言偏好 |
| 配置已保存中文，本次临时要求英文 | 英文 | 不更新，技能默认语言仍为中文 |
| 用户明确要求将技能默认语言从中文改为英文 | 英文 | 将 `config.json` 中的 `language` 更新为 `"en"` |

用户选择其他语言后，仍按首版支持范围处理。当前计划使用了某种语言，不代表技能配置已经被修改；持久化偏好和生成本次产物是两项不同的操作。

### 配置保存和更新

发行版提供初始 `config.json`。运行时配置文件或 `language` 字段不存在，按尚未设置偏好处理；只有用户明确同意保存时，创建或更新该配置项。不得把临时选择、未回复或默认英文视为保存授权。用户可以在以后明确要求修改或重置该字段。

这里的“全局”限定为同一份技能安装目录：调用这份技能的不同项目共用其配置，不同安装副本之间不会自动同步。若多个用户共用同一安装目录，也会共用该配置。配置文件只存技能设置，不混入任务、需求或历史计划数据。

安装提供初始配置，后续更新保留用户已有配置与其他字段；新增项使用内置默认值并说明含义，不无条件覆盖已保存偏好。

配置读取和保存使用独立辅助脚本，保存操作保留其他配置项，采用原子替换；生成器仅消费已解析的计划输入。非法非空语言值或损坏的配置应明确报告并处理，不能当作已确认的有效偏好。保存失败时，当前计划仍可按已选语言生成，但必须说明全局偏好没有保存成功。

## 输入和输出契约

在顶层增加可选字段 `language`，继续使用输入 `version: 1`。旧输入结构仍可接受，但省略字段时的显示语言改为英文，行为兼容性变化需明确说明。

| 字段或行为 | 约定 |
| --- | --- |
| `language` | 仅接受字符串 `zh-CN` 或 `en`；主代理将自然语言偏好映射到这两个值 |
| 字段省略 | 独立运行生成器时规范化为 `en`；技能流程应先解析偏好，再显式填写本次语言 |
| 无效值 | 计划输入中的显式 `null`、空字符串、错误类型及其他语言码均按输入错误处理，CLI 返回 2；技能配置中的 `language: null` 是有效的未设置状态 |
| `schedule.json` | 保存规范化后的 `language`，供展示和审查共用 |
| `unit` 省略 | 随语言使用“相对工作单位”或 `relative work units` |
| `unit` 已提供 | 生成器保留原值；主代理负责确保它符合目标语言和相对工作量语义 |
| HTML | `lang` 与规范化语言一致 |
| SVG | 用目标语言生成标题、描述、图例及提示，并提供相应 `xml:lang` |

例如，英文规划使用：

```json
{
  "version": 1,
  "language": "en",
  "title": "Data export",
  "summary": "Provide asynchronous CSV exports and a download entry point.",
  "unit": "relative work units"
}
```

这是顶层字段示意，完整输入仍需包含现有契约要求的其他字段。

只切换语言时，任务 ID、需求 ID、依赖、资源锁名称和所有排程数字保持一致。资源名参与精确匹配，不应为了显示翻译而改变，否则可能改变互斥关系。若以后需要可翻译的资源展示名，应另行设计显示映射。

原始需求文件继续逐字保留。产物中明确标注的原文引用、代码、产品名、路径和标识符可以保留原语言；主代理撰写的摘要、任务说明、验收条件、风险和假设使用目标语言。需求条目可按现有契约忠实改写为目标语言，并保留可定位的来源。

## 生成器改造

在 `project-planner/scripts/locales/` 增加 `zh-CN.json` 和 `en.json`，作为生成器固定显示文案的集中来源。采用 Python 标准库读取，以脚本位置定位目录，避免依赖当前工作目录或引入外部翻译服务。

文案包含完整句子的命名占位符，例如任务数量、相对终点和阻塞条件；不要通过逐个翻译中文词语再拼接句子构造英文。两种语言覆盖相同文案键及兼容的占位符。

生成器的职责是选择固定文案并显示输入内容，不调用模型翻译任务正文。主代理在填写输入时完成正文语言适配。

| 改造位置 | 具体工作 |
| --- | --- |
| `validate_plan` | 校验并规范化本次 `language`，字段省略时使用 `en`；按语言解析省略的 `unit` |
| `build_schedule` | 将 `language` 传递到排程对象，调度逻辑继续只使用原有调度数据 |
| Markdown 渲染 | 本地化标题、章节、表头、状态、默认空值、节点类型展示名和相对工作量说明 |
| SVG 渲染 | 本地化标题、无障碍描述、图例、状态、工具提示、页脚及右侧详情文案 |
| HTML 渲染 | 本地化页面文案、表头、按钮、详情标签、状态、默认空值和无障碍标签；设置语言属性 |
| HTML 交互 | 从同一语言文案源生成客户端标签和状态映射，避免 JavaScript 再维护另一份翻译 |

JSON 中的 `task`、`milestone`、`external`、`scheduled`、`blocked` 等协议值保持不变，在人类可见位置使用显示文案。审查返回的 `PASS`、`REVISE`、`INCOMPLETE` 同样作为固定协议值保留。

把所需文案完整解析后再进入文件写入阶段。缺少语言资源或必需文案时明确失败，避免生成一部分英文、一部分中文的产物。原有 HTML、JSON、SVG 和 Markdown 转义机制继续覆盖本地化内容及插值数据。

CLI 帮助和底层诊断文案不作为首版必须全部本地化的范围；用户收到的最终说明由主代理按适用的交流语言提供。后续可以单独完善命令行语言体验。

## 图表布局

当前 SVG 的图例使用固定横坐标，任务标签和右侧详情使用固定截断长度。英文文案可能更长，替换文字后必须重新检查布局。

首版按以下方式处理：

- 图例根据显示文案长度分配间距，必要时换行，并同步调整图表顶部位置。
- 长说明使用分行、简明措辞或合理增加可用宽度，确保“条长表示工作量，横轴不表示现实时间”的解释在独立 SVG 中也能读到。
- 任务名和交付物允许缩略显示，但通过 SVG 工具提示和 HTML 详情保留全文。
- 保持既有相对轴及条长比例，不为翻译改变排程值。

最终检查实际渲染的中英文 SVG 和 HTML，包括长任务名、多个资源、未知外部事件、里程碑、空计划以及详情弹窗。查看源码不能代替视觉检查。

## 独立审查改造

审查模板新增明确的目标语言参数，并要求审查者与 `plan-input.json`、`schedule.json` 中的 `language` 相互核对。主代理填写模板时同时提供语言选择的简短依据，区分本次明确选择、已存全局偏好、已有计划语言和默认英文，避免无父上下文的审查者猜测用户偏好。审查者不直接读取可能变化的全局配置，以本次输入固定的语言为审查对象。

审查者检查：

1. 主代理撰写的规划内容与目标语言一致，需求原文引用和标识符等合理例外得到保留。
2. Markdown、SVG 和 HTML 固定文案使用同一语言，HTML 与 SVG 的语言属性正确。
3. 翻译没有改变需求含义、工作量语义、依赖门槛和阻塞状态。
4. 长文案没有造成图例、标签、说明或弹窗重叠与裁切。

审查者使用目标语言返回说明，主代理用目标语言撰写 `review.md`；其中固定结论值保持英文。`review.md` 记录目标语言及选择依据，连同现有模型参数、视觉证据和哈希快照保存。

审查语言不由英文提示词隐式决定。首版模型仍为 `gpt-6.1-sol`，推理强度为 `high`，`fork_turns="none"`。采用 `max_review_revisions` 时，在启动初次审查前固定本次修订轮次上限，并记录到 `review.md`，运行期间修改全局默认值不改变本次审查约定。轮次上限不会取消视觉检查、哈希检查或未通过时的草稿标记。语言字段属于输入和排程文件的内容，纳入既有哈希检查；切换语言、改写正文或重新生成后，重新执行完整独立审查。

## 英文权威指令

针对国际开源受众，建议将 `SKILL.md` 的描述和正文，以及执行时必须阅读的 `references/schema.md`、`references/review.md` 一并迁移为英文权威版本。只翻译入口而留下强制中文参考文档，会使英文读者仍无法完整理解和贡献。

英文的主要收益是方便能阅读英文的国际使用者审阅、反馈和修改。没有依据仅凭语言就断言模型执行更可靠；指令的清晰程度、契约一致性和实际行为验证更值得关注。

OpenAI 的技能文档要求 `name`、`description` 和工作流指令，并强调明确范围、输入输出及行为测试；该文档没有规定必须使用英文。因此，英文权威版本是本项目面向国际受众的维护选择，而非平台要求。[OpenAI 技能文档](https://learn.chatgpt.com/docs/build-skills)

建议的文件语言分工如下：

| 内容 | 建议语言策略 |
| --- | --- |
| `SKILL.md` | 单一英文权威版本，集中定义输出语言选择规则 |
| `references/schema.md` 和 `references/review.md` | 英文权威版本，与入口保持一致 |
| `agents/openai.yaml` | 面向国际分发采用英文显示名、简介和默认提示；保留显式调用策略，不让默认提示强制英文产物 |
| `README.md` | 英文使用和贡献入口 |
| `README.zh-CN.md` | 中文使用说明，与英文 README 的能力声明同步 |
| 生成产物 | 使用确定并记录的输出语言 |
| 项目内部设计记录 | 继续使用当前维护者偏好的简体中文 |

首版不额外维护一整套中文技能指令副本，降低两份执行规范漂移的成本。中文读者通过中文 README 了解用法及语言规则。已有中文示例可以保留，并增加一份英文示例用于展示和验证。

迁移时逐项核对输入输出、文件保护、禁止创建 Issue/PR、独立审查要求及完成门槛，确保翻译保留约束的强度。英文迁移作为独立实施阶段，已包含在用户本次按方案更新的授权内。

## 实施顺序和文件范围

| 阶段 | 修改范围 | 完成条件 |

| 2 确定性生成与配置辅助 | build_plan.py、新增 locales 文案资源、配置辅助脚本 | 配置读取和授权保存独立于生成，本次有效设置明确记录，三种展示使用完整文案，HTML 与 SVG 属性正确 |
| 3 行为和视觉验证 | test_build_plan.py、配置辅助脚本测试、补充英文测试输入 | 通过配置读写、语言及调度回归检查，实际查看中英文图表和交互 |
| 4 使用说明 | 两份 README、agents/openai.yaml、中英文示例输入与产物 | 说明 config.json 的作用、英文默认值及授权保存流程，中文示例明确语言，安装完整包含配置、语言资源与辅助脚本 |
| 5 英文指令迁移 | SKILL.md、两份 references、界面元数据 | 英文指令保留既有行为，中文与英文请求均能得到正确语言产物 |

阶段 1 到 4 构成可独立交付的语言适配；阶段 5 属于建议的开源维护改进。两部分可以分别形成可审阅变更，不需要依赖新的任务或工作树工作流。

## 验收场景

| 场景 | 预期结果 |
| --- | --- |
| 独立运行旧输入，无 `language` 和 `unit` | 正常生成英文固定文案，默认单位为 `relative work units`；输入正文由调用者保证语言一致 |
| config.json 不存在或其中 `language: null` | 询问偏好与保存意愿，无其他明确选择时按英文继续；不因默认值创建或修改技能配置 |
| 用户只选择中文，没有同意全局保存 | 当前输入记录 `zh-CN`，全局偏好不变 |
| 用户同意保存中文 | config.json 的 `language` 更新为 `zh-CN`，其他配置项保留，下次新计划采用中文且不重复询问 |
| 已保存中文，本次临时指定英文 | 当前计划使用英文，全局中文偏好保留 |
| 用户同意保存，但保存失败 | 当前计划使用已选语言，明确报告全局保存未成功 |
| 技能配置中 `max_parallel: 3`，新项目未指定容量 | 本次规划按最多三个普通任务同时开展排程，并说明容量来自技能默认配置 |
| 技能默认容量为 3，本次项目明确容量为 2 | 按两个任务并行规划，不自动修改技能默认容量 |
| `max_review_revisions` 为 0 | 仍执行初次完整审查；发现实质问题时交付待决草稿，不声称审查通过 |
| 更新技能时已有用户配置 | 保留已保存的语言和其他设置，新增字段使用默认值 |
| 新输入使用 `zh-CN` | 规划、图表和报告说明使用简体中文 |
| 新输入使用 `en` | 正文、固定文案和交互使用英文，默认单位为 `relative work units` |
| 中文对话明确要求英文产物 | 主代理写入 `en`，原始中文需求保持原样，审查说明使用英文 |
| 英文指令配合明确中文输出要求或已存中文偏好 | 输出采用 `zh-CN`，不因指令语言转为英文 |
| 更新英文计划且未要求切换语言 | 保留已记录的英文输出语言 |
| 使用不支持或错误类型的语言值 | 在写入前报输入错误，CLI 返回 2，不静默回退 |
| 同一图结构仅切换语言和显示正文 | 任务 ID、依赖、资源锁、状态、起止、阻塞链及 makespan 相同 |
| 长英文任务名和阻塞说明 | 图表可读，没有重叠或裁切，详情全文可查看 |
| 正文包含 Unicode 和 HTML 特殊字符 | 按原有安全转义显示，不破坏 SVG、HTML、Markdown 或内嵌 JSON |
| 原文引用和标识符使用另一种语言 | 不被误判为语言不一致，不因翻译改变来源或资源语义 |

脚本验证沿用 `python -X utf8 -m unittest discover -s tests -v`，补充有实际行为意义的语言测试和中英文排程对照。技能文件使用 skill-creator 的校验工具检查元数据；该检查不能代替行为验证。

使用简体中文与英文请求分别做一次完整规划验证，核对生成、独立审查、视觉检查及最终哈希。方案文档本身不触发技能的强制规划审查；实施后的真实规划验证按技能流程执行。

## 交付判断

语言适配完成需要同时满足语言契约、实际产物、独立审查和使用说明的一致性。仅修改 SKILL.md 的一句规则、仅翻译任务正文，或仅设置 HTML 的语言属性，都不足以完成本次改造。

英文指令迁移的判断标准是国际读者能完整读懂执行路径，同时中文用户仍能得到中文产物。维护清晰的一份权威指令，并让使用文档和输出语言分别服务各自读者，是建议采用的长期策略。
