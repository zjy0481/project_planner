# Code review 与宏观系统审查：实践和证据

调研日期：2026-10-07。本文区分组织实践指南、经验研究和架构评估方法；三者都不能保证无缺陷。

## 结论

Google 把变更级审查的目标定为持续改善系统代码健康，而非追求完美。审查要覆盖设计、用户功能、复杂度、测试、命名、注释、风格和文档，并结合整文件与系统上下文。操作上先理解变更意图、优先看关键设计，再逐行理解负责范围；界面行为可要求演示，安全、并发等专门领域应有胜任的审查者。重要设计问题应尽早反馈，避免先花时间细审将被推翻的实现。[审查维度与做法](https://google.github.io/eng-practices/review/reviewer/looking-for.html)；[批准标准](https://google.github.io/eng-practices/review/reviewer/standard.html)

小变更应聚焦一个可独立理解、测试且提交后系统仍可用的目标。Google 同时描述按文件、水平、垂直及混合方式拆分；这说明切分应看依赖、并行空间和可审性，不存在唯一正确轴。拆分后的每一步仍需保持构建可用。[Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)

## 经验研究与适用边界

Bacchelli 与 Bird 对 Microsoft 的现代审查做了探索性混合方法研究：观察 16 个团队中的 17 名工程师，访谈并分类 200 个讨论串的 570 条评论，另调查 165 名经理和 873 名程序员。找缺陷是常见动机；但评论样本中 78/570（14%）被归为缺陷发现，且主要是低层逻辑问题。研究还发现，理解变更缘由与上下文是审查的主要挑战；知识传递、团队认知和替代方案也是审查收益。建议给审查者更多系统背景、邀请了解代码的人参与，并让作者在变更说明中交代缘由；不清楚时用同步沟通补足纯 diff 工具的局限。[原文 PDF（作者所在机构托管）](https://www.ifi.uzh.ch/dam/jcr:4d711d23-ce10-4069-8214-eae91797e44b/icse2013.pdf)

边界要说清：这是单一公司、单一工具生态的探索性研究；14%是被分析评论的类别占比，不是缺陷检出概率、审查有效率或跨组织定律。它支持“不要把 review 当作可靠的单一质量闸门”，不支持“review 无效”。

## 宏观系统评估

当问题涉及性能、可用性、安全性、可修改性等质量目标之间的系统级取舍时，普通 PR 逐行审查不足以表达全部问题。SEI 的 ATAM 先收集业务驱动和架构，再把质量目标细化为有优先级的场景，逐项分析架构方案，记录风险、非风险、敏感点和权衡点，并向利益相关者报告。SEI 描述的典型评估需受训团队与多类利益相关者，通常约三至四天；因此它适合重要架构决策的专门评估，不是每次提交的例行步骤。[SEI ATAM 方法与输出](https://www.sei.cmu.edu/library/architecture-tradeoff-analysis-method-collection/)

## 可落地建议

1. 让变更说明写清目标、背景、影响范围、关键设计选择和验证方式；审查先读说明，再看主路径和测试。
2. 先审目标是否正确、设计是否合系统，再审行为边界、错误路径、并发和测试是否真能暴露失败；最后检查命名、注释、风格与文档。
3. 按独立性与依赖拆分工作，水平、垂直或混合皆可；保持每个中间提交可构建，避免把大规模重排与功能变更混在一起。
4. 将确定性检查交给自动化；人工时间留给上下文理解、设计取舍、测试有效性和高风险领域，并明确各审查者覆盖范围。
5. 对跨模块或多质量属性决策另开架构评估，采用场景和风险记录；把它与日常变更审查衔接，而非混成更长的 PR 清单。

来源性质：Google Engineering Practices 是组织实践规范；Bacchelli–Bird 是经验研究；SEI ATAM 是架构评估方法说明。研究与方法来源均有明确适用范围，不构成任何审查方式能彻底保证质量的证据。
