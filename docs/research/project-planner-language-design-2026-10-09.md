# Project Planner 语言支持是否需要专门适配？

日期：2026-10-09

## 结论

“语言不影响计划流程”对排程算法成立，对当前完整产物链不成立。当前模型负责编写计划输入，Python 生成器负责计算排程并渲染 Markdown、SVG、HTML；生成器中的标题、说明、图例、状态、详情弹窗等固定文案不会因为要求模型跟随对话语言而改变。因此，当前架构仍需要语言适配，但不需要把语言保存为跨项目的全局偏好，也不需要按语言改变排程算法。

建议保留已有中英双语文案目录，将有效语言限定为单次计划的属性；删除或不再要求 `config.language: null` 的询问与全局保存流程。选择顺序可采用：本次明确的产物语言、被更新计划的既有语言、当前对话的主要语言；对话混杂或目标不明确时才询问。将解析后的语言写入计划输入和排程，以供渲染器设置固定文案及 HTML/SVG 语言属性，并让无父上下文的审查者知道审查目标。跟随当前对话语言是合理的产品默认建议，尚未经过本项目的跨语言行为评测，不能描述为自动判断绝对可靠。

只支持中文和英文时，维护现有 catalog 是改动最少、确定性最高的方案。若目标变为跟随任意语言，可评估让模型每次提供受约束的文案数据、再由脚本确定性渲染；这需要新增接口、键和占位符校验、HTML 转义、文案快照与视觉验证，并非零适配，也不比当前双语目录更小。让模型直接生成整个 HTML/SVG 也不是获得多语言固定文案的必要条件。

## 本地实现核查

核查范围是工作区 `dev` 分支上已存在的未提交实现，以及基线 `abb6acd7a086047194174acdbdca33f3286a5460`。之前批准的语言方案仅作为待重新评估的背景；本结论来自当前职责分工和官方文档，不把既有设计决定当作必要性的证明。

| 层 | 代码事实 | 对语言设计的影响 |

基线脚本在 `abb6acd7a086047194174acdbdca33f3286a5460` 的 `project-planner/scripts/build_plan.py:382–437, 515–521` 已包含中文 Markdown、甘特图和详情弹窗文案。这说明固定文案的本地化需要来自原有脚本渲染架构，不是最近的双语改造才引入的问题。

## 方案取舍

| 方案 | 适用范围和成本 | 主要限制 |
| --- | --- | --- |
| 保留中英 catalog，模型写计划正文，脚本排程和渲染 | 当前仅要求中文/英文时改动最少；离线可用、渲染可复现，也容易验证两种语言的固定标签。 | 新语言要新增并审查完整文案目录；支持范围仍是枚举值。 |
| 模型提供受约束的固定文案对象，脚本确定性渲染 | 若明确要支持 catalog 之外的语言，可避免为每种语言长期维护一份完整 JSON 文件；HTML/SVG 结构和排程仍保持确定性。 | 需定义稳定的键和占位符契约、校验缺失/多余键和格式、转义值、将本次文案保存成快照以供重渲染和审查，并验证长文本布局。每次重新生成文案可能变化，因此不能依赖“再问一次模型”保持复现。 |
| 模型直接生成 Markdown、SVG 或 HTML | 可尝试最大限度由模型按本次语言写所有内容。 | 不只是语言适配；排程状态、数值、依赖、图表与计划正文可能不一致，还需处理结构、转义、可访问性、离线行为、视觉检查与哈希复现。若计划仍由脚本计算，模型生成甘特图也可能与权威 schedule 脱节。对于多语言标签来说成本和风险都高于提供固定文案数据。 |

## 建议的最小语言契约

1. 将语言视为计划的展示设置，而不是影响需求拆解、任务依赖或排程的项目全局设置。
2. 删除“配置为 `null` 时先询问是否设全局默认”的必经流程。每次按明确语言、现有计划语言、对话主要语言解析；仅在混合或歧义时问本次，不默认保存跨项目偏好。
3. 保留 `plan-input.json` / `schedule.json` 中的有效语言字段，因为脚本靠它选择固定文案并设置语言属性，审查者靠它确认目标语言。配置未指定时按对话语言作默认属于产品决策；若仍仅支持两种语言，遇到其他目标需先说明支持范围或明确扩展策略。
4. 保留现有中英 catalog 和占位符校验，直到有真实需求证明需要任意语言。若需要扩展，优先评估模型生成受约束的文案对象并快照保存，继续让 Python 处理排程及文件安全；无需先把图表/HTML整体交给模型生成。
5. 用代表性的中英文对话、混合语言需求、显式与隐式语言选择、更新已有计划、较长文案和各类图表状态评估语言行为。观察到稳定失败后再增加规则或动态文案机制。

## 外部证据与推论边界

- OpenAI 将 skill 描述为重复工作流的指令和资源层，可定义调用时机、步骤、如何处理不完整结果及最终输出；该模型说明支持“先用清楚的工作流指令约束模型正文”的做法，但没有要求保存语言偏好或采用某种语言。[Skills 概念文档](https://developers.openai.com/plugins/concepts/skills)
- OpenAI 的 skill 构建指引要求写明输入、步骤、输出、不可推断事项和何时询问；建议在需要确定性计算或文件处理时使用脚本，且当指令和已有工具足以可靠完成时不要额外加脚本。[Build skills](https://developers.openai.com/plugins/build/skills)
- Prompt Engineering 文档说明 `instructions` 可以规定模型生成回复时的行为、语气和目标；另一节明确指出生成是非确定性的，并建议通过测试和评估观察行为变化。[Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering)
- OpenAI 的准确性指南建议从简单提示和预期输出开始，再按观察到的错误增加上下文、指令或例子；指南称摘要、翻译和代码生成有时只靠提示即可达到生产水平，但这不是对本项目、特定计划任务或某次模型的保证。[Optimizing LLM Accuracy](https://developers.openai.com/api/docs/guides/optimizing-llm-accuracy)
- OpenAI 关于 GPT-6 Astra 的文章建议避免过度细化工作流说明，同时明确区分了 Astra 与 Sol / Luna 的影响。[Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra) 本笔记不把 Astra 专属经验泛化为 `gpt-6.1-sol` 或 Luna 会自动选对语言的证据。

据此推论：明确要求输出语言是模型生成正文的合理控制手段，通常应先评估这种较简单做法；但 OpenAI 文档既不保证模型可靠地自动镜像对话语言，也不能消除当前确定性 renderer 对固定文案的语言依赖。默认“跟随当前对话主要语言”是本项目可验证的交互策略，不是平台强制规范。
